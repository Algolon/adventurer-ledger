# M2.1 interaction with the M1.4 rules engine

Status: implementation note for the M2.1 character vertical slice

## Summary

M2.1 ships the Brammel level 1–2 slice on the merged M1.4 engine **without
changing `src/rules/*`, `src/domain/model.ts` or `src/domain/content-pack.ts`.**

That is not the same as saying the engine has no open findings. The correct
statement is:

> The synthetic Vanguard level 1–2 slice functions on the current M1.4 engine by
> using authoring patterns that avoid the five independently reproduced pilot
> gaps. M2.1 neither invalidates nor repairs those findings.

None of G-1 through G-5 is addressed in this branch. They remain open against the
shared engine and belong to a separate public M1.5 mechanics correction.

## The five findings and how M2.1 avoids each

### G-1 — option-grant activation

**Finding.** Entries granted through an option-grant effect are not activated by
the effect runtime in every path a pilot exercised.

**How M2.1 avoids it.** Every option that must contribute effects is selected
through a normal `ChoiceDefinition` whose option carries either an `entryId` or
inline `effects`. Choice resolution activates the selected entry through the
ordinary selected-entry path, which works today. The synthetic fighting style and
weapon mastery both use this pattern.

**Not fixed here.** Content that relies on an option grant to activate an entry
still behaves as the finding describes.

### G-2 — multiple and partial recharge

**Finding.** Resources needing more than one recharge trigger, or a partial
recharge, are not fully expressed.

**How M2.1 avoids it.** The synthetic resource recharges fully on a single
trigger: Rallying Breath returns on a short rest and nothing else. The runtime
service only restores resources whose declarative recharge matches the rest being
applied.

**Not fixed here.** A resource needing partial or multi-trigger recharge is still
unexpressible.

### G-3 — one resource-maximum convention

**Finding.** More than one representation of a resource maximum is possible, and
M1.4 does not prevent conflicting representations.

**How M2.1 avoids it.** The slice uses exactly one convention: the class
progression writes a level-keyed maximum into `resource.<id>`, and the resource
definition reads it through a `path` value. The resolver reads the same path.

**Not fixed here.** M1.4 still accepts content that mixes conventions, and
nothing in this branch detects or rejects that.

### G-4 — duplicate diagnostics

**Finding.** The engine can report the same underlying problem more than once.

**How M2.1 avoids it.** The resolver surfaces sanitized issue codes and the UI
groups them by severity, so a duplicated engine diagnostic is visible but not
misleading. M2.1 does not deduplicate engine issues.

**Not fixed here.** This is presentation tolerance, not an engine correction.

### G-5 — origin ability-score increases

**Finding.** Origin increases are not derived by the engine.

**How M2.1 avoids it.** The increase is captured by the M2.1 creation contract
rather than by rules evaluation. The draft records the standard-array assignment
and the origin increases separately and stores the resulting final scores, and
the planner validates that some assignment of the ruleset's array plus the
origin's declared increase pattern reproduces those finals. The engine is handed
final scores.

**Not fixed here.** No derivation of origin increases was added to M1.4.

## Consequence for scope decisions

Because these five findings are untouched, M2.1 must not be read as evidence
that the shared engine is complete. A public M1.5 mechanics correction and any
broader content pilot still need their own gate.
