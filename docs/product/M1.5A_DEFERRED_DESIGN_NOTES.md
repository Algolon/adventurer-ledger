# M1.5a deferred design notes

Three things this branch deliberately did not build. Each needs a decision that
would be expensive to reverse once data exists, so the reasoning is recorded here
rather than settled by whatever the first implementation happened to do.

Nothing here describes official rulebook content. The examples use the public
original synthetic fixtures.

## 1. Rolled and manual scores plus origin increases

### The problem

A draft currently stores three things: `abilityBaseScores` (the standard-array
assignment), `abilityIncreases` (the origin's increases keyed by ability) and
`abilityScores` (the finals). That works because the standard array is a fixed
multiset, so the planner can check that *some* assignment of it plus the origin
pattern reproduces the finals.

Rolled and manual scores break that check. There is no multiset to validate
against, so `abilityScores` becomes unverifiable and the relationship

```text
base score method + origin allocation = final score
```

stops being reconstructible from what is stored. This is the same ownership
question as the open M1.5 pilot gap G-5: the engine does not derive origin
increases, and M2.1 handed it final scores instead.

### The decision that has to be made first

Who owns the equation. Three shapes, and they are not equivalent:

1. **Store the finals only.** Simplest, and what M2.1 does. Cannot show the user
   where a score came from, cannot revalidate after an origin change, and cannot
   distinguish "rolled a 17" from "typed a 17".
2. **Store base plus increases, derive the final.** Provenance is complete and
   an origin change recomputes correctly. Requires every ability method to
   produce a base, including rolled — which means storing the roll result as
   durable data, with all the trust questions that carries.
3. **Store all three, validate the relationship.** What the array path does now.
   Needs a per-method validator; for rolled scores the only honest validator is
   "the user asserts this", which is a different kind of record.

### Recommendation

Option 2, with the method recorded alongside the base so a rolled base is
visibly a rolled base. It is the only shape that keeps origin increases
recomputable, which is what G-5 will need whenever it is fixed.

**No schema change in this branch.** Adding a base-score field before G-5 has an
owner would mean writing durable data whose meaning is still undecided.

## 2. Custom equipment and loadout editing

### The problem

Equipment today is either granted by a bundle or selected from a bundle choice.
There is no way to add an item the content does not mention, and no durable
distinction between four genuinely different states:

- **granted** — the content gave it to you, and re-resolving would give it again;
- **selected starting equipment** — you picked it from a choice at creation;
- **manually owned** — you acquired it in play, and no content justifies it;
- **equipped / carried** — where it currently is, independent of the above.

`CharacterInventoryItem` currently carries a single writable `equipped` flag,
which the M1.4 report already noted is one writable carry state and deliberately
not a second representation of bundle status.

### Why it cannot be added incrementally

The four states are not a flag, they are a provenance axis crossed with a
location axis. Collapsing them loses information that cannot be recovered:

- re-resolving content must not delete a manually owned item;
- changing a starting-equipment choice must remove what the old choice granted
  and nothing else;
- a level-up that grants equipment must not duplicate an item already held;
- an export must be able to say which items the content justifies.

Guessing at this now means a migration later over data whose provenance was
never recorded, which is exactly the case where the information does not exist
to migrate from.

### Recommendation

A separate branch that introduces provenance on the inventory record before any
custom-equipment UI. Until then, equipment stays content-driven, which this
branch keeps working correctly: automatic grants display, real choices are
presented, and the step is omitted when there is nothing to choose.

## 3. Hit-point finalization during creation

### The problem

Maximum hit points are affected by a known per-level Constitution defect. A
creation UI that let the user "finalize" current or maximum HP would let them
compensate for a wrong number — and once they had, the wrongness would be
indistinguishable from a deliberate table ruling. Fixing the formula afterwards
would then silently change characters whose owners had already worked around it.

### What the eventual design has to cover

- **Automatic maximum.** Derived, explainable, and the only source of the
  maximum. No creation-time editing of it.
- **Current defaults to maximum.** On commit, current HP is the maximum. This is
  already true and should stay true.
- **Optional current-HP finalization before commit.** Legitimate for a character
  joining mid-campaign. It must adjust *current* only, never maximum, and must
  be visibly a manual current value rather than a derived one.
- **Preservation through later level changes.** The preserve-deficit policy
  already handles this for level-up; a manually finalized current value has to
  enter that policy as a deficit, not as a new baseline.

### Recommendation

Do not build any of it until the Constitution defect is fixed. The correct order
is: fix the formula, confirm the automatic maximum is right, then add optional
current-HP finalization on top of a maximum nobody needs to work around.

**This branch adds no HP UI**, which keeps that order available.
