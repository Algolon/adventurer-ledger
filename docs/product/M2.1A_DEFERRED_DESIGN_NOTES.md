# M2.1a deferred design notes

Things the real-content creation foundation deliberately did not build, and the
reasoning behind each. Every one needs a decision that would be expensive to
reverse once durable data exists, so the argument is recorded here rather than
settled by whatever the first implementation happened to do.

Nothing here describes official rulebook content. All examples use the public
original synthetic fixtures in `tests/fixtures/`.

Status is stated per item. **Deferred** means not built and not planned in this
branch. **Partly resolved** means the branch built part of it and the rest is
still open; the open part is named explicitly so nothing here reads as done when
it is not.

## 1. Base scores, origin increases, and the methods that produce them

**Status: partly resolved. Rolled scores and multiple increase patterns remain
deferred.**

### What is now true

A draft stores three things, and the relationship between them is enforced
rather than assumed:

- `abilityBaseScores` — the scores before any origin contribution;
- `abilityIncreases` — the increases the user placed, keyed by ability;
- `abilityScores` — the finals.

`reconcileAbilityAllocation` in `src/services/ability-allocation.ts` derives the
finals from the first two and validates the increases against the pattern the
active origin declares. An increase whose ability or amount the current origin
does not offer is reported as `ORIGIN_INCREASE_NOT_AVAILABLE` and excluded from
the finals, and the commit writes the planner's finals rather than the draft's
stored ones. That closes the case the earlier design could not express: an
origin change used to leave the increase it authorised silently baked into a
score.

A draft written before base scores existed is not stranded. The base is
reconstructed as `final − stored increase`, which is the exact inverse of how
the final was produced, so a draft with no increases is left untouched.

### What is still open

**Rolled scores.** There is still no rolled method. Rolling produces a base with
no multiset to validate against, so `standardArrayConsistent` has nothing to
check and the only honest validator is "the user asserts this" — a different
kind of record from a derived one. The shape that works is to store the roll
result as durable data with the method recorded alongside it, so a rolled base is
visibly a rolled base. That is a schema addition, and it should not be made
before the method it describes exists.

**Multiple increase patterns (pilot gap G-5).** `abilityIncreases` is keyed by
ability, so each slot is identified by its *amount*. That is sound for a pattern
whose amounts are distinct, such as +2/+1, and it is what the acceptance fixture
declares. A pattern with repeated amounts — three separate +1s — cannot be
represented, because two slots would collide on one key. Fixing it means keying
the draft field by slot rather than by amount, which is a durable-data change and
belongs with the broader G-5 work rather than smuggled in beside it. The
validator already refuses such an allocation rather than accepting it wrongly:
the second increase of a repeated amount is reported as `slot-already-used`.

## 2. Inventory provenance

**Status: deferred.**

### The problem

Equipment is either granted by a bundle or selected from a bundle choice. There
is no way to add an item the content does not mention, and no durable
distinction between four genuinely different states:

- **granted** — the content gave it to you, and re-resolving would give it again;
- **selected starting equipment** — you picked it from a choice at creation;
- **manually owned** — you acquired it in play, and no content justifies it;
- **equipped / carried** — where it currently is, independent of the above.

`CharacterInventoryItem` carries a single writable `equipped` flag, which the
M1.4 coverage report already recorded as one writable carry state and
deliberately not a second representation of bundle status.

### Why it cannot be added incrementally

The four states are not a flag. They are a provenance axis crossed with a
location axis, and collapsing them loses information that cannot be recovered:

- re-resolving content must not delete a manually owned item;
- changing a starting-equipment choice must remove what the old choice granted
  and nothing else;
- a level-up that grants equipment must not duplicate an item already held;
- an export must be able to say which items the content justifies.

Guessing now means a migration later over data whose provenance was never
recorded — the case where the information does not exist to migrate from.

### What this branch did instead

It fixed the presentation half without touching the durable half.
`equipmentGrantsFor` now emits one view per **bundle** with a `grantedBy` list,
and `selectedEquipmentFor` counts each bundle once and totals items per
`(item, status)`. Two entries granting the same kit produce one kit with two
recorded sources, rather than two kits — which is a display and derivation fix,
not a provenance model. The provenance axis is still not durable, and adding it
still belongs to its own branch before any custom-equipment UI.

## 3. Hit-point finalisation during creation

**Status: deferred, and deliberately so.**

### The problem

Maximum hit points are affected by a known per-level Constitution defect. A
creation UI that let the user "finalise" current or maximum HP would let them
compensate for a wrong number — and once they had, the wrongness would be
indistinguishable from a deliberate table ruling. Fixing the formula afterwards
would then silently change characters whose owners had already worked around it.

### What the eventual design has to cover

- **Automatic maximum.** Derived, explainable, and the only source of the
  maximum. No creation-time editing of it.
- **Current defaults to maximum.** On commit, current HP is the maximum. This is
  already true and should stay true.
- **Optional current-HP finalisation before commit.** Legitimate for a character
  joining mid-campaign. It must adjust *current* only, never maximum, and must be
  visibly a manual current value rather than a derived one.
- **Preservation through later level changes.** The preserve-deficit policy
  already handles this for level-up; a manually finalised current value has to
  enter that policy as a deficit, not as a new baseline.

### Ordering

Fix the formula, confirm the automatic maximum is right, then add optional
current-HP finalisation on top of a maximum nobody needs to work around. This
branch adds no HP UI, which keeps that order available.

## 4. Ruleset profile identity, and the collision that was not migrated

**Status: corrected going forward; existing profiles deliberately not migrated.**

`rulesetIdForPack` derived a profile ID by stripping a leading `pack:`, so
`rulesetIdForPack("pack:x")` and `rulesetIdForPack("x")` both produced
`ruleset:x`. Two unrelated packs mapped to one profile: the second import would
either be refused as a duplicate of a pack it has nothing to do with, or
overwrite the profile an existing character is resolved against.

The derivation now keeps the pack ID whole, which is injective — distinct pack
IDs always produce distinct profile IDs, including prefix-related and visually
similar ones.

**Existing profiles are not rewritten.** A profile ID is referenced by every
committed character through `rulesetProfileId`, so changing stored IDs would mean
a migration across characters, drafts, derived snapshots and transfer documents
to repair a collision that requires two specifically-named packs to trigger. That
is a strictly larger compatibility risk than the defect. Instead
`legacyRulesetIdsForPack` reports what the old derivation would have produced,
and the install boundary checks every candidate before creating anything — so a
pack whose profile was created under the old scheme is recognised as already
installed and is never silently duplicated or overwritten.

The residual limitation, stated plainly: a device that already holds profiles for
both `pack:x` and `x` created under the old derivation has one profile where it
should have two, and this branch does not repair that. It refuses to make it
worse.

## 5. Ruleset membership by entry identity

**Status: corrected for new profiles; existing profiles keep source scoping.**

A profile scoped its content by `activeSourceIds`. Because two packs may
legitimately publish against the same source, importing one pack activated every
installed entry sharing its source — widening a character's ruleset with content
nobody chose.

New profiles now record `allowedEntryIds`, the bounded set taken from the pack
actually installed, and `scopeEntriesToRuleset` uses it when present. Declared
dependencies join that set only through the typed `ResolvedDependency` mechanism,
where the caller supplies the dependency's entries explicitly.

Profiles written before this keep source scoping and resolve exactly as they did.
That is intentional — retro-fitting an entry set onto an existing profile would
change which content an existing character resolves against, which is the failure
this change exists to prevent. The open question deferred here is whether a
future migration should offer to narrow such a profile, with the user confirming
the change per character rather than having it applied silently.
